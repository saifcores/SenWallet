# M3 — Outbox et événements

Branche : `milestone/m3-outbox-events` · Taille : M

## Ce qui a été construit

- **Contrats** (`platform/event-contracts`, package `sn.senwallet.events`) : enveloppe `event_id`, `event_type`, `occurred_at`, `trace_id`, `aggregate_id`, `version`, `payload` ; types `ledger.transaction.pending`, `.posted`, `.archived`. La charge utile est une notification (`transaction_id`, `external_id`, `ledger_id`). Schémas JSON dans `src/main/resources/schemas/`. `trace_id` reste nul jusqu'à M10. ADR-21.
- **Outbox** (`V2__outbox.sql`) : `id` identity pour l'ordre du relais, `event_id` unique pour le consommateur, index partiel des lignes non publiées. `ledger_app` peut insérer et ne mettre à jour que `published_at`.
- **Écriture** : `OutboxPort.append` dans la transaction de posting, de contre-passation et de transition (`pending → posted | archived`). Un rejeu ou une transition inchangée n'ajoute rien ; un refus n'ajoute rien non plus.
- **Relais** : `OutboxRelay` lit `FOR UPDATE SKIP LOCKED` (lot de 100), publie sur l'exchange topic durable `ledger` avec confirmations, puis pose `published_at`. Un échec de confirmation annule le timbre. `OutboxRelayScheduler` est coupé dans les tests d'intégration existants (`ledger.outbox.relay-enabled=false`).
- **Broker** : RabbitMQ 4 dans Compose (utilisateur `senwallet`, port 5672). Le service ledger l'attend avant de démarrer.
- **Consommation** (`platform/event-inbox`) : `IdempotentInbox.claim` insère dans `processed_events` et n'exécute le handler que si l'insert gagne, dans la transaction de l'appelant. Le script SQL est prêt à être copié par les services (M4). Pas encore de consommateur wallet.
- ArchUnit ignore `sn.senwallet.events` au même titre que le noyau partagé : les contextes peuvent dépendre du langage publié, pas les uns des autres.

## Tests

- Unitaires : sérialisation snake_case de l'enveloppe pour les trois types ; append mémoire (un événement à la création, aucun au rejeu, un à la transition, un à la contre-passation, aucun si la condition échoue).
- `OutboxRelayIT` : cinq postings, le relais confirme deux messages puis lève une exception (`published_at` reste nul), un second passage publie les cinq. Le consommateur de test, lié à `ledger.#` avant toute publication, applique chaque `event_id` une seule fois. Un handler qui échoue annule aussi le claim. En SQL brut comme `ledger_app`, `UPDATE` du `payload` et `DELETE` sont refusés (`42501`).

## Ce qui a été appris

- Un UUID v4 ne peut pas ordonner le lot. L'identity et l'`event_id` ont deux rôles (ADR-21).
- La confirmation du broker arrive avant le `COMMIT` qui pose `published_at`. Un arrêt au milieu du lot laisse des messages déjà dans RabbitMQ et des lignes non timbrées : le second passage republie, l'inbox absorbe le doublon.
- L'utilisateur `guest` de RabbitMQ refuse toute connexion qui ne vient pas du conteneur lui-même. Compose et Testcontainers se connectent en `senwallet`.
- Spring Boot 4 expose le bean d'administration sous le type `AmqpAdmin`.

## Ce qui reste

- M4 : le wallet copie `processed_events.sql` et consomme `ledger.transaction.*` pour l'historique et les notifications.
- `trace_id` sera rempli avec le traçage (M10).
- Les comptes `async` sont toujours verrouillés avec les autres ; les `balance_deltas` arrivent en M10.
