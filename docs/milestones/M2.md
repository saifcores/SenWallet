# M2 — Persistance du ledger et API

Branche : `milestone/m2-ledger-persistence` · Taille : L

## Ce qui a été construit

- **Domaine** (`ledger-domain`, toujours en Java pur) : `LedgerTransaction` porte le ledger, une description, des métadonnées, `reversesId` et `archivedAt` ; `restore(...)` reconstruit depuis la base sans événement ; `reversal(...)` crée la contre-passation d'une transaction `POSTED`. Nouvel agrégat `Ledger`. Les ports suivent l'algorithme : `insertIfAbsent`, `lockForUpdateSorted`, `insertEntries` (avec la version de chaque compte), `updateStatus`, `findByIdForUpdate`.
- **Application** (`ledger-application`, seulement `spring-tx`) : cas d'usage créer un ledger, ouvrir un compte, poster, faire transiter, contre-passer, lire les soldes (courants ou `as_of`). `RequestHasher` calcule un SHA-256 d'une forme canonique de la requête. `TransactionWriter` applique les étapes 3 à 6 de la section 4 du dossier dans une seule transaction PostgreSQL.
- **Schéma** (`V1__ledger_schema.sql`) : tables de la section 3, enums, index (dont GIN sur `metadata`), `ledger_entries` partitionnée par mois, garde-fous en base (déclencheurs de contrainte différés d'équilibre, immuabilité des écritures, transitions `pending → posted | archived` seulement, `CHECK >= 0`), droits du rôle applicatif. Ajouts au DDL du dossier : ADR-18 ; partitions : ADR-19 ; rôles : ADR-20.
- **Infrastructure** : dépôts `JdbcClient` en SQL explicite (ADR-13), verrous `FOR UPDATE OF b ... ORDER BY a.id`, `BalanceRecomputeQuery` (recalcul des quatre seaux depuis les écritures, réutilisable par le `DriftScanner` de M8), `JdbcBalanceHistory` (soldes `as_of`), `PartitionMaintainer`.
- **API REST** (JSON snake_case, montants entiers) : `POST/GET /ledgers`, `POST/GET /ledger_accounts`, `GET /ledger_accounts/{id}/balances?as_of=`, `POST /ledger_transactions` (201 ou 200 au rejeu), `GET` et `PATCH /ledger_transactions/{id}`, `POST /ledger_transactions/{id}/reversal`. Erreurs en `ProblemDetail` avec `type = urn:senwallet:problem:<code>`. Contrat : [`contracts/openapi/ledger.yaml`](../../contracts/openapi/ledger.yaml).
- **Boot** : `UseCaseConfig` déclare les handlers ; Flyway en `ledger_owner`, la source de données en `ledger_app` ; Actuator ; `Dockerfile` sur `eclipse-temurin:25-jre` ; service `ledger` dans Compose (port 8002).
- **Build** : `platform/test-support` (un PostgreSQL 16 Testcontainers par JVM, initialisé par le même script que Compose) et le plugin de convention `senwallet.integration-test` (suite `integrationTest`, incluse dans `check`).

## Tests

- Unitaires de l'application sur les dépôts en mémoire : rejeu, conflit 409, transitions (y compris le rejeu d'une transition), contre-passation unique, hash canonique.
- Intégration (`ledger-boot/src/integrationTest`) contre PostgreSQL 16 :
  - `CountersMatchEntriesIT` (exercice 3) : 2 000 opérations aléatoires (dépôts, P2P conditionnés, transitions, contre-passations) ; pour chaque compte, les compteurs égalent le recalcul depuis les écritures.
  - `IdempotencyIT` (exercice 4) : 1 000 rejeux séquentiels puis 50 premiers appels simultanés sur threads virtuels ; une seule ligne `ledger_transactions`, deux écritures, une seule réponse 201 ; un corps différent donne 409.
  - `ConcurrencyIT` (exercice 5) : 100 débits HTTP simultanés de 20 000 sur 1 000 000 XOF avec `available >= 0` → exactement 50 × 201 et 50 × 422, disponible final 0, aucun seau négatif. 200 P2P croisés A→B / B→A en parallèle sans interblocage.
  - `DatabaseGuardrailsIT` : en SQL brut comme `ledger_app`, `UPDATE`/`DELETE` sur `ledger_entries` refusés (`42501`), écritures déséquilibrées refusées au `COMMIT` (`23514`), `posted → pending` refusé, colonnes non autorisées refusées, partition `DEFAULT` vide.
  - `LedgerApiIT` : allers-retours 201/200/409/422/404/400, transitions, contre-passation, soldes `as_of`.
  - `OpenApiContractIT` : le contrat est valide et liste exactement les opérations des contrôleurs.
- ArchUnit : le domaine ne dépend ni de l'application ni de l'infrastructure, l'application ne dépend pas de l'infrastructure et n'utilise de Spring que `org.springframework.transaction`, aucun JPA dans le ledger.

## Ce qui a été appris

- Une transition de statut verrouille d'abord la ligne de la transaction (`findByIdForUpdate`) : deux `PATCH` simultanés ne règlent pas deux fois.
- `INSERT ... ON CONFLICT DO NOTHING` attend la fin d'une insertion concurrente de la même clé : les 50 premiers appels simultanés produisent un 201 et 49 rejeux, sans erreur.
- En PL/pgSQL, `CASE ... THEN NEW.id ELSE NEW.transaction_id` échoue sur la table qui n'a pas la colonne : un déclencheur par table, une fonction de contrôle partagée.
- PostgreSQL 16 accepte les déclencheurs de contrainte sur une table partitionnée ; ils sont clonés sur chaque partition, y compris celles créées plus tard.
- En M2, tous les comptes d'une transaction sont verrouillés, y compris les comptes `async` ; les `balance_deltas` (mise à jour différée des comptes chauds) arrivent en M10.
