# M5 — Passerelle, Keycloak, jetons de service

Branche : `milestone/m5-gateway-security` · Taille : S

## Ce qui a été construit

- **Keycloak** (image officielle 26.3) : realm `senwallet` importé depuis
  [`deploy/keycloak/senwallet-realm.json`](../../deploy/keycloak/senwallet-realm.json).
  Rôles `customer`, `ops`, `finance`, `compliance`, `approver`. Utilisateurs
  de test (dont Adama). Clients `wallet-web` (public, password grant,
  audience `wallet`) et `wallet-service` (client credentials, audience
  `ledger`). `payments-service` et `recon-service` sont présents, désactivés.
- **Traefik** v3, file provider, pas de socket Docker : TLS sur 443,
  `PathPrefix(/api)` → wallet avec `StripPrefix`, quota par en-tête
  `Authorization`. Aucune route vers le ledger. ADR-23.
- **Ledger** : OAuth2 Resource Server, audience `ledger`. Santé Actuator
  ouverte. Sans jeton, l'API répond 401.
- **Wallet** : Resource Server, audience `wallet`, rôle `customer`.
  `POST /customers` reste public. Client credentials vers le ledger via
  `OAuth2AuthorizedClientManager` ; `LedgerClient` envoie `Authorization`
  et rejoue un 401 pour prendre un jeton frais. 409 et 422 ne sont pas
  rejoués.
- **Tests** : `SenwalletKeycloak` (un conteneur par JVM, même realm que
  Compose). Les IT du ledger parlent en `wallet-service`. Les IT du wallet
  envoient le jeton `customer`. Exercices 4–6 sur l'API wallet.

## Tests

- Ledger : un POST sans jeton → 401 ; avec jeton de service, le comportement
  M2/M3 inchangé (idempotence, concurrence, garde-fous).
- Wallet : inscription sans jeton → 201 ; `POST /transfers` sans jeton → 401.
  Exercice 6 : plafond 4 000 000 XOF, 422, aucune transaction `p2p:{id}`.
  Exercice 4 : même clé et même corps, une seule transaction ; corps
  différent → 409.
  Exercice 5 : 100 P2P concurrents de 20 000 (frais 200) depuis 1 010 000 XOF
  → 50 × 201, 50 × 422, disponible 0.
- Compose : Keycloak, Traefik, wallet et ledger sains. `https://localhost/api`
  sans jeton → 401. POST ledger sans jeton → 401. Un P2P authentifié passe
  par la passerelle.

## Ce qui a été appris

- Traefik OSS ne vérifie pas les JWT ; le ledger doit le faire lui-même
  puisqu'il n'est pas derrière la passerelle (ADR-23).
- L'`iss` du jeton doit matcher l'issuer configuré, mais le JWKS peut être
  chargé depuis une autre URL. Compose pinne Keycloak sur
  `http://localhost:8080` (jetons smoke / README) et pointe
  `jwk-set-uri` / `token-uri` vers `http://keycloak:8080`. Les tests pinent
  un port hôte et passent `--hostname=http://127.0.0.1:<port>`.
- `pg_advisory_xact_lock` n'est pas concerné. Un 401 ledger doit être un
  échec de transport (rejeu) et non un 4xx métier, sinon le client garde un
  jeton mort.
