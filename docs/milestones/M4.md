# M4 — Wallet, KYC, plafonds, frais, P2P

Branche : `milestone/m4-wallet-p2p` · Taille : L

## Ce qui a été construit

- **Domaine** (`wallet-domain`, Java pur) : `Customer` (téléphone E.164, palier `N1` / `N2` / `MERCHANT`, non vérifié ou vérifié), `Wallet` (`opening` ou `active`, compte ledger, alias PI-SPI local = le téléphone), `Transfer` (`posted` ou `rejected`). `LimitPolicy` et `FeeSchedule` sont choisies par `valid_from <= maintenant`, la ligne la plus récente l'emporte. La commission est `montant * taux`, half-up, via `Money` : 50 000 XOF donnent 500. `P2pPosting` débite l'émetteur de `montant + frais`, crédite le bénéficiaire du montant, et crédite le compte de frais quand la commission est positive. Les conditions (`available >= 0`, `pending <=` plafond) partent vers le ledger ; le wallet ne juge pas les soldes.
- **Schéma** (`V1__wallet_schema.sql`) : clients, wallets, transferts, politiques datées (plafond 4 000 000 XOF au 2026-11-02 pour les trois paliers, P2P à 1 %), clés d'idempotence, `processed_events` copié de `platform/event-inbox`, historique, ligne unique `platform_accounts`. Rôles `wallet_owner` (Flyway) et `wallet_app` (exécution), script `deploy/postgres/init/02-wallet.sh`. Persistance `JdbcClient`, pas de JPA (ADR-22).
- **Application** : inscription (OTP simulé renvoyé dans la réponse), vérification au palier N1 qui ouvre le compte ledger puis le wallet, montée de palier simulée, lecture du wallet et de l'historique, envoi P2P. La clé d'idempotence réserve le `transferId` au premier passage : un rejeu après le posting ledger réutilise `p2p:{transferId}`.
- **Client ledger** (`platform/ledger-client`, package `sn.senwallet.clients.ledger`) : création du ledger, ouverture de compte, posting, lecture. Le posting a un délai de 2 secondes et un retry sur timeout et 5xx, avec le même `external_id`. 409 et 422 ne sont pas rejoués. Jackson 3, snake_case. ArchUnit ignore `sn.senwallet.clients` comme `sn.senwallet.events`.
- **API** (port 8001, sans jeton) : `POST /customers`, `POST /customers/{id}/verification`, `POST /customers/{id}/kyc`, `GET /wallets/{id}`, `POST /transfers` (`Idempotency-Key`), `GET /wallets/{id}/history`. Contrat [`contracts/openapi/wallet.yaml`](../../contracts/openapi/wallet.yaml). Erreurs en `ProblemDetail`, `type = urn:senwallet:problem:<code>`.
- **Consommation** : file `wallet.ledger` liée à `ledger.#`. `IdempotentInbox.claim` et l'historique partagent une transaction. Une ligne d'historique et un SMS simulé (journal `sn.senwallet.wallet.sms`) par wallet touché. Un second passage n'insère rien.
- **Compose** : service `wallet` sur 8001, qui attend Postgres, RabbitMQ et le ledger.

## Tests

- Domaine : 50 000 → 500 ; la politique respecte `valid_from` ; le posting P2P a trois écritures et deux conditions.
- Application, ports en mémoire : rejeu, 409 si le corps change, aucun appel ledger si la clé est déjà terminée, aucun client local si l'ouverture du compte ledger échoue.
- Intégration (`WalletApiIT`), PostgreSQL et RabbitMQ Testcontainers, ledger réel :
  - exercice 6 : bénéficiaire déjà à 4 000 000 XOF, P2P de 1 XOF → 422, aucune transaction `p2p:{id}` ;
  - SendCash interne : l'émetteur est approvisionné par un posting ledger direct de 100 000, puis `POST /transfers` de 50 000 → disponible 49 500, bénéficiaire 50 000, compte de frais 500 ;
  - même clé et même corps : une seule transaction ; corps différent : 409 ;
  - un `ledger.transaction.posted` écrit une ligne d'historique et un SMS par wallet ; une réémission du même message n'ajoute rien.
- `./gradlew build` vert, ArchUnit compris.

## Ce qui a été appris

- `pg_advisory_xact_lock` renvoie `void`. Le mapper JDBC qui lit un `long` échoue (`Bad value for type long`) : il faut parcourir la ligne sans lire la colonne.
- Le compte ledger est ouvert avant l'insertion locale. Si l'insertion échoue ensuite, le compte à solde nul reste : le ledger n'a ni ouverture idempotente ni clôture dans ce jalon.
- La confirmation RabbitMQ peut précéder le `COMMIT` de l'outbox (M3). L'inbox du wallet absorbe le doublon.
